# Slay the Spire 2 Modding: Can You Build an "AI Companion" for Co-op?

**A feasibility and implementation research report — October 2026**

**Scope:** a **host-only mod compatible with vanilla guests**; no guest-side mod is in scope unless a real need emerges later.

**Design decisions locked in** (rationale in §5.2):

1. The host player chooses the agent's character in the lobby.
2. Agents abstain from map votes and collaboration-event votes (or follow the host player's vote).
3. In combat, agents act only when the host triggers them via a host-only UI button; the host can also wake an agent that has already ended its turn (the mod's control layer cancels its own end-turn confirmation — no agent involvement) and have it act again, e.g. after it gained new cards.
4. Interactive events (Crystal Sphere and similar minigames) are de-minigamed: the mod solves the interaction locally and presents the agent with outcome-level choices, then plays out the chosen sequence as ordinary game actions (§3.1).

---

## TL;DR

**Yes — it is doable, and the proof already exists in public.** Slay the Spire 2 (Early Access since March 5, 2026) ships with an **integrated mod loader**, gained **official Steam Workshop support** in June 2026, and exposes its entire C# game logic to mods via the bundled `sts2.dll` plus Harmony patching. The scoped design — **a host-only mod whose AI companion looks like an ordinary player to vanilla guests** — is consistent with everything publicly known about the consistency check and wire protocol: the join check hashes *content*, which a content-free companion mod never touches, and KitLib's dev toolkit already demonstrates a host-fabricated "phantom player" sharing a lobby with a real remote client. The one thing nobody has publicly confirmed is that combination inside a Steam P2P lobby — which is a single prototype experiment, not a research project. Prior art covers every other subsystem: **sts2AITeammate** runs multiple AI-driven characters in one host process (MIT-licensed), **STS2-Agent** and **neuro-sts2** put an AI-driven instance into real lobbies (Neuro-sama did it on stream), **STS2MCP** exposes the whole game as an agent API with multiplayer support, and Plapla's **Couch Co-op** — the mod you remembered — proves a "player" needn't be a game client at all.

## 1. The Game and Its Modding Interface Today

### 1.1 Engine, release status, and official mod support

Slay the Spire 2 launched into Steam Early Access on **March 5, 2026**, rebuilt from scratch on the **Godot 4.5.1 engine with C# (.NET 9)** — a deliberate departure from the original's Java/LibGDX stack, motivated in part by the Unity runtime-fee controversy and by moddability ([Yelzkizi](https://yelzkizi.org/slay-the-spire-2-godot-engine-switch-explained/)). The launch was enormous: Mega Crit reported **3 million units sold and over 25 million runs within the first week**, and the studio immediately committed to a roadmap that included Workshop support and multiplayer quality-of-life work ([Yahoo Tech](https://tech.yahoo.com/articles/slay-spire-2-merely-week-231748396.html)). For a modder, the commercial momentum matters mostly as a guarantee that the Early Access period (estimated 1–2 years) will be actively patched — which cuts both ways, as Section 5 discusses.

The critical fact for this report is that modding is not a hack bolted onto StS2 — it is a shipped feature. In the patch notes for Major Update 2 (v0.107.1), Mega Crit stated: *"We built STS2 with modding in mind, and the game has had an **integrated mod loader from day one**,"* while admitting they deliberately under-advertised it until it was ready ([slaythespire.wiki.gg](https://slaythespire.wiki.gg/wiki/Slay_the_Spire_2:V0.107.1_-_Major_Update_2)). That same update, released **June 19, 2026**, added full **Steam Workshop support** with an official upload tool for creators, and hundreds of mods appeared within weeks ([Player.One](https://www.player.one/slay-spire-2-major-update-introduces-steam-workshop-support-gameplay-fixes-163411), [Rogueliker](https://rogueliker.com/slay-the-spire-2-steam-workshop-rng-bestiary/)). There is no ModTheSpire-style external loader as in StS1; the game simply shows a Mods option on the main menu and flags itself as "RUNNING MODDED" ([Steam Discussions](https://steamcommunity.com/app/2868840/discussions/0/567037624436648209/)).

### 1.2 How a mod is actually built

The modding toolchain is well documented by the community. A mod is a folder dropped into a `mods/` directory next to the game executable, containing a **manifest JSON**, optionally a **compiled .NET 9 DLL** referencing the game's own `sts2.dll`, and optionally a Godot **`.pck`** resource pack for assets and native UI. The manifest declares an `id`, `has_dll`, `has_pck`, `dependencies`, and a notable boolean — **`affects_gameplay`** — which the game uses to distinguish cosmetic/client-side mods from simulation-relevant ones. Code entry is via the `MegaCrit.Sts2.Core.Modding` namespace and a `[ModInitializer("MethodName")]` attribute; the game even bundles `0Harmony.dll`, so **Harmony runtime patching** is a first-class technique for altering behavior the official hooks don't cover ([jiegec/STS2FirstMod](https://github.com/jiegec/STS2FirstMod)).

Because the game's logic ships as a managed .NET assembly, the full internal API surface — combat state machines, player objects, command dispatch, networking — is inspectable with a standard decompiler (ILSpy), and the community has produced a version-tracked **modding handbook** documenting the loader contract, semantic hooks, model discovery, and worked examples for cards, relics, potions, events, and GUI overlays, verified against build v0.103.3 ([StS2 Modding Tutorial](https://fresh-milkshake.github.io/Modding-Tutorial/)). The same tutorial warns, accurately, that Early Access updates can change signatures and loader contracts between patches, so a released mod must be re-validated against `sts2.dll` on every game update. Supporting infrastructure has matured quickly too: an open-source mod manager handles modpacks and version pinning across Nexus, Workshop, and GitHub sources ([STS2 Mod Manager](https://mohamedserhan.github.io/sts2-mod-manager/)), and foundation libraries like BaseLib and RitsuLib provide shared APIs. In short, the "modding interface" you asked about is real, documented, and — thanks to the un-obfuscated C# assembly — effectively total: anything the game's own code can do, a mod can do, the only question being effort and patch fragility.

## 2. How Multiplayer Actually Works Under the Hood

### 2.1 The architecture, from the engineer who built it

Mega Crit has been unusually transparent about the netcode: the engineer responsible for the co-op mode published a detailed development retrospective. Three design facts from it decide the feasibility of your AI companion. **First, UI and game logic are strictly separated** — Godot nodes are used only for visual representation, and all gameplay logic lives in C#, which is exactly what makes a "player without a screen" a meaningful concept in this codebase. **Second, the simulation is built on deterministic execution over a Commands-and-Hooks system**: players don't share a live world — each instance runs the same deterministic simulation, and what travels over the wire is each participant's *commands*. **Third, the transport is a Steam P2P layer**, friends-only by design ([straypixels.net](https://straypixels.net/sts2-multiplayer-timeline/)).

The consequence is profound for modding: in this architecture, **a "player" is nothing more than a source of well-formed actions** plus a slot in the lobby. A human produces actions through the UI; nothing stops a mod from producing them through code. This is why every AI-teammate project converges on the same trick, and it also explains why the game tolerates such different client shapes — full game instances, emulated in-process players, even web browsers.

The determinism article adds two operational facts that shape the whole design. **First, only actions cross the wire — never state.** Each peer re-executes every action locally; there is no "result" message to fabricate, and directly mutating game state on the host would be invisible to guests at best and fatal at worst: after every deterministic action, all peers checksum their state and a mismatch disconnects the client with a "Your state diverged!" popup ([straypixels.net](https://straypixels.net/sts2-multiplayer-determinism/)). **Second, the safe posture for the mod therefore writes itself: issue vanilla actions on the phantom's behalf and read everything; never alter deterministic execution.** Any Harmony patch that changes *what* executes or *in what order* on the host (timing mismatches are the hardest divergence class) risks kicking your friends mid-run. The bonus: since remote players' actions arrive as discrete ordered messages, your agent gets a clean, screen-scrape-free event stream of everything happening in the run — ideal policy input.

### 2.2 Constraints that shape your design

Vanilla co-op is **2–4 players over Steam friends invites, with no matchmaking and no built-in local/couch co-op**; the host owns the save file, all original players must be present to resume a run, and you cannot add anyone mid-campaign ([PC Gamer](https://www.pcgamer.com/games/roguelike/slay-the-spire-2-multiplayer-co-op/), [IGN](https://www.ign.com/wikis/slay-the-spire-2/How_Multiplayer_Co-Op_Works)). Co-founder Casey Yano confirmed in a Reddit AMA that couch co-op was simply not considered for Early Access ([IGN](https://www.ign.com/wikis/slay-the-spire-2/Biggest_Changes_in_Slay_the_Spire_2)) — which is precisely the gap your remembered mod filled. Each player runs an independent deck/relic/gold state inside a shared combat and map, and all players act simultaneously during a shared turn, ending when everyone confirms ([Mobalytics](https://mobalytics.gg/slay-the-spire-2/guides/co-op-multiplayer)). For your AI companion this means it must participate in *every* decision point a human would: card plays, end-turn confirmations, map votes, reward picks, shop visits, campfire choices, and event options.

Two further constraints matter practically. The **4-player lobby cap** counts every participant, so "you + 2 friends + 1 AI" fills a vanilla lobby exactly; if you want a bigger party plus AI, the community **Remove Multiplayer Player Limit** mod raises the cap to as high as 16 and even reworks shops, campfire seating, and difficulty scaling for larger groups — though all players must run the same mod version for it to function ([Rain156/sts2-RMP-Mods](https://github.com/Rain156/sts2-RMP-Mods)). And there is the **mod-consistency question**: the community consensus is that client-side mods (the `affects_gameplay` distinction) only affect the player who has them, while gameplay-affecting mods must match across the whole lobby or sessions desync and crash ([Reddit](https://www.reddit.com/r/slaythespire/comments/1te7ko1/do_mods_work_in_co_op_slay_the_spire_2/), [XMODHub](https://www.xmodhub.com/info/blog/best-slay-the-spire-2-mods-guide/)). Where the companion mod lands on that spectrum determines whether guests can stay vanilla — §4.2 dissects this in detail.

## 3. Your Idea Already Exists — In Pieces

### 3.1 sts2AITeammate: multiple programmatic players in one host process

The closest existing artifact to your plan is **sts2AITeammate** by SallyHong2347 (Nexus Mods, MIT-licensed source on GitHub). It *"adds AI-controlled teammates to a local fake-multiplayer run"* — the mod starts what is internally a multiplayer session, but the additional party members are emulated locally and driven by a heuristic AI that handles combat turns, card rewards, potions, shops, and many events, with per-character JSON behavior configs so different companions play differently ([Nexus Mods](https://www.nexusmods.com/slaythespire2/mods/366)). This is a direct, working answer to your core question — *"is it possible to run multiple characters on one host, with some of them controlled programmatically?"* — and the answer is unambiguously yes: the game does not require each party member to correspond to a separate process, account, or human.

Its limits are equally instructive. The author is candid that the AI is experimental, not a strong strategist, that some events fall back to conservative generic behavior, and that *"multiplayer-adjacent flows are more fragile than ordinary combat loops"*. Notably, **Crystal Sphere — the fortune-teller event built around a Minesweeper-style grid-reveal minigame rather than a menu choice — has no handler at all**: the mod excludes `CrystalSphere` from AI event pools for release safety ([GitHub](https://github.com/SallyHong2347/sts2-ai-teammate)). That is structural evidence, not laziness: the action layer is built around single-shot decision points, and this event is a stateful multi-step interaction (spend 3–6 divinations revealing an 11×11 grid, then pick among uncovered rewards ([wiki](https://slaythespire.wiki.gg/wiki/Slay_the_Spire_2:Crystal_Sphere))) with a genuine hang risk — vanilla itself needed an "occasional Crystal Sphere softlock" fix pre-release. For a host-only mod with vanilla guests, exclusion is *not* an available strategy (removing content touches ModelDb and breaks the content-free rule of §4.2), so interactive events need bespoke handling. The locked design for Crystal Sphere follows the report's core principle — **convert the minigame back into choices**: the mod solves tile placement itself (the grid layout is deterministic state, readable from host memory or reconstructable from the run seed — a local read, fully within §2.1's posture), evaluates candidate bundles against the phantom's current deck/relic needs, and presents the agent with 2–3 *outcome-level* choices (e.g. "3 divinations: rare+uncommon+common cards" vs "rare+uncommon cards + rare potion"); a simpler variant offers only a budget choice (cautious/greedy) and lets the solver maximize value. The mod then plays out the chosen placement as ordinary reveal/claim actions, which guests' sims re-execute as an unremarkable Crystal Sphere run. Placement must indeed be solved *before* presenting choices, since overlapping 3×3 reveals can surface extra rewards that change the agent's preference. Crucially for you, the current release targets **solo play with bots** — it does not mix emulated AI players with real remote friends in one lobby. That exact combination is the unclaimed territory your mod would occupy.

### 3.2 STS2-Agent and neuro-sts2: an AI teammate as a second local instance

A second proven topology comes from **STS2-Agent** (CharTyr), distributed via Steam Workshop. From the main menu you click **"Invite AI Teammate"** and the mod launches an isolated second game instance on the same PC, which joins your co-op lobby through the game's **internal multiplayer test lobby** (the launcher passes `--force-steam off` and steps the `clientId` so the two instances don't collide). You play your character in window one; an OpenAI-compatible LLM plays its own character in window two — and it even supports **natural-language team chat**, so you can type "focus the right cultist" and the companion adapts subsequent decisions ([CharTyr/STS2-Agent](https://github.com/CharTyr/STS2-Agent)). The project's Option C is also notable for developers: with no model configured, the teammate instance still joins and readies up, then simply waits — exposing its own `GET /state` / `POST /action` HTTP endpoints so *any* external program can drive that character.

The same pattern underlies **neuro-sts2**, VedalAI's open-source mod that wired the AI VTuber **Neuro-sama** into StS2. The mod observes the current game context, registers valid actions for each decision point, sends them to the Neuro runtime over a websocket, and validates and executes the returned choice; it ships dedicated command-line flags — `--multiplayer-host`, `--multiplayer-join <steam name>`, `--multiplayer-join-any` — specifically to automate lobby behavior for a machine-controlled client ([VedalAI/neuro-sts2](https://github.com/VedalAI/neuro-sts2)). This is not a theoretical demo: Neuro and Evil Neuro have played StS2's co-op mode live with a human partner on stream ([YouTube](https://www.youtube.com/watch?v=g4lA_dujxMk)). Between these two projects, the "second instance on the host PC, driven by an external brain" design can be considered a solved engineering problem, including the fiddly parts like resuming saved co-op runs without corrupting the host-owned save.

### 3.3 STS2MCP: the agent-API approach, with co-op support

The third family is **agent-interface mods**: rather than embedding a brain, they expose the game as an API and let you bring your own. The leading example, **STS2MCP** (≈500 GitHub stars), starts an HTTP server on `localhost:15526` serving structured game state and legal actions, with an optional MCP server so tools like Claude Code can play directly. Its feature list explicitly covers multiplayer: profile and character select for host and client, seed selection, **multiplayer host, Steam-friend join, and FastMP localhost join**, plus resuming saved co-op lobbies ([Gennadiyev/STS2MCP](https://github.com/Gennadiyev/STS2MCP)). The author's own stated motivation will sound familiar: *"I start building this mod with the hope that I can co-op with an AI player."*

Two practical lessons emerge from this project. One is that multiplayer support in agent mods is the fragile frontier — the author labels it beta and asks users not to report mod-caused desyncs to Mega Crit. The other is cost: driving a full run with a frontier LLM is not cheap, with the author measuring **slightly over 8 million tokens for a complete Claude run and ~7.3M for GPT** — a heuristic bot like sts2AITeammate's is free and instant, an LLM companion is smart but metered. For your use case (a companion that plays *alongside* humans at human pace), a hybrid is attractive: heuristics for routine turns, an LLM only for genuinely strategic nodes, or a small local model via the OpenAI-compatible endpoints STS2-Agent supports.

### 3.4 The couch co-op mod you remember — and what it proves

Your recollection was correct, and it was about StS2, not StS1. The **"Couch Co-op"** mod by **Plapla** on the Steam Workshop *"turns phones, tablets, and laptops on your local network into browser-based clients for multiplayer"* — only the host needs the mod (or even the game installed, for participants), because the host runs the entire simulation and serves each participant a thin browser client ([Steam Workshop collection](https://steamcommunity.com/sharedfiles/filedetails/?id=3747911499), [Instagram](https://www.instagram.com/popular/couchup/)). (If you were thinking further back, the StS1-era equivalent was the online co-op mod **Spire with Friends**, which supported up to 6 players in co-op via Steam connectivity ([Spire With Friends Wiki](https://spire-with-friends.fandom.com/wiki/Spire_With_Friends_Wiki)).)

The Couch Co-op mod is the strongest public evidence that the host's authority in StS2's networking is near-total: participants don't need a game client at all, just something that renders state and returns decisions. Swap "browser on a phone" for "decision function in a mod" and you have your AI companion — the architectural distance is zero. Two caveats are worth noting honestly: parts of the community criticize this mod for effectively distributing the game to non-owners, so treat it as a technical reference rather than something to emulate wholesale ([note.com](https://note.com/l1nc3/n/n9d9b7d49fe43?hl=en)); and a separate, uncontroversial project — the **LAN multiplayer mod** — demonstrates the transport layer itself can be cleanly replaced via Harmony patches, which is another route for injecting a local pseudo-client ([Nexus Mods](https://www.nexusmods.com/slaythespire2/mods/579)).

## 4. Feasibility Verdict for Your Exact Scenario

### 4.1 Three proven paths, one unbuilt combination

![Three implementation paths](sts2_three_paths.png)

Your scenario — *"me and my friends in a multiplayer lobby, plus an AI character controlled programmatically, all running from my host"* — decomposes into three architectures, each already demonstrated publicly. The table below consolidates the comparison.

| Path | How it works | Proven by | Friends can join? | Friends need mods? | Main trade-off |
| --- | --- | --- | --- | --- | --- |
| **A. In-process fake players (chosen design)** | One host process emulates extra party members; the mod generates their decisions | sts2AITeammate ([Nexus](https://www.nexusmods.com/slaythespire2/mods/366), [GitHub](https://github.com/SallyHong2347/sts2-ai-teammate)); KitLib phantom player ([GitHub](https://github.com/WRXinYue/STS2-DevMode)) | KitLib shows phantom + real client coexisting (LAN/test transport); Steam lobby unproven | **No — if the mod stays content-free** (§4.2) | Cleanest UX (single instance); one unproven link; must re-verify after every EA patch |
| **B. Dual instance on the host PC** | Second game instance on your machine joins via the internal local test lobby (`--force-steam off`, stepped `clientId`); a mod drives it | STS2-Agent ([GitHub](https://github.com/CharTyr/STS2-Agent)), neuro-sts2 ([GitHub](https://github.com/VedalAI/neuro-sts2)) | Yes — they join your lobby via Steam as usual; the AI instance is just another lobby member | No — the AI instance is content-free, so the consistency hash stays vanilla (§4.2) | Most robust and shipping today; costs a second game process (~extra RAM/CPU) and the AI occupies a lobby slot |
| **C. External agent via API** | Any client in the lobby runs an agent mod exposing state/actions over localhost HTTP/MCP; an external program (LLM, script, RL agent) decides | STS2MCP ([GitHub](https://github.com/Gennadiyev/STS2MCP)), Neuro SDK | Yes — same as B; C is essentially "the brain for B's second instance" | No — same reasoning; the agent mod lives only on the AI's instance | Maximum flexibility of "brain" (any language/model); LLM token costs and latency at human play pace |

The honest verdict: **Path B/C is buildable this weekend by assembling existing, shipping parts**, and is the natural fallback if Path A hits a wall. **Path A — the chosen design, AI players simulated inside the host process alongside remote vanilla friends — has no shipped implementation**, but every subsystem it requires is proven somewhere: fake-player emulation (sts2AITeammate), phantom-in-a-mixed-lobby mechanics (KitLib, §4.2), transport manipulation (LAN mod, Couch Co-op), and the command-based simulation that makes a headless player a first-class citizen (the engine architecture itself). The gap is one integration step, not a missing capability.

### 4.2 Can the guests stay vanilla? The consistency check, dissected

The community folklore "everyone must run the same mods" is real but imprecise. The join handshake verifies a **content fingerprint** — a hash over the content database (`ModelIdSerializationCache`) — and since Major Update 2 (v0.107.1), mods flagged `affects_gameplay: false` are **excluded from that hash**, producing at most a *"non-gameplay mod mismatch warning"* rather than a block; the hard "Mod Mismatch" error is reserved for gameplay-affecting content differences such as cards, relics, or characters one side lacks ([slaythespire.wiki.gg](https://slaythespire.wiki.gg/wiki/Slay_the_Spire_2:V0.107.1_-_Major_Update_2), [Steam guide](https://steamcommunity.com/sharedfiles/filedetails/?id=3559414134)). The deeper constraint is not the handshake but the **deterministic simulation**: all peers run the same sim and diverge if content IDs or RNG sequences differ — which is exactly why even identical mod sets desync when load order differs ([Reddit](https://www.reddit.com/r/slaythespire/comments/1rzeqhj/psa_how_to_fix_desync_error_in_slay_the_spire_2/)). A companion mod that **registers no content models** — no cards, relics, or characters in ModelDb — and only fabricates a player slot while issuing legal commands leaves the serialized simulation identical to vanilla. To a guest's sim, the phantom is indistinguishable from a fourth human who plays fast.

That this works mechanically is no longer hypothetical. The KitLib dev toolkit ships **"Pseudo Co-op Test (Host)"** with an optional **phantom player (NetId 1001)** driven by an AI teammate, plus **SyncBot**, which "simulates remote peer ACKs and default choices on one machine… for host-only co-op smoke tests without a second client" ([WRXinYue/STS2-KitLib](https://github.com/WRXinYue/STS2-DevMode)). A lobby member is a NetId plus a stream of commands and ACKs, and the host can fabricate all three. The mixed case has even been hit — and fixed — in the wild: KitLib 0.32.0 patched "a real LAN client joining as player 1001 is no longer mistaken for the phantom companion… fixing combat desync when both players take their own turns" — a bug that only exists because a **real remote client and a host-fabricated phantom were sharing one lobby**, i.e. exactly the target topology. Three caveats remain: flagging the mod `affects_gameplay: false` while it plainly alters play stretches the flag's plain-English meaning (its de-facto semantics are "alters content/serialization," which the mod genuinely does not — but Mega Crit could tighten this in any patch); the phantom-plus-vanilla-guests combination is publicly demonstrated on the LAN/test transport, **not yet on a Steam P2P lobby** — that is the first thing to prototype. Also: fabricate ACKs only for the phantom, never for real clients — precisely the desync bug KitLib fixed.

The third caveat deserves its own paragraph because it is a **v1 requirement for any group that saves and resumes regularly**. The host-owned save lists the phantom as a run participant, and vanilla resume requires all original players present — but the vanilla Load flow opens the run over Steam networking, rejects the phantom's non-Steam player ID, and renames the save as corrupt. This is documented behavior, not conjecture: STS2-Agent hit exactly this and ships its own continue button to bypass the stock flow ([CharTyr/STS2-Agent](https://github.com/CharTyr/STS2-Agent)). Your mod must therefore **own the continue path**: intercept or replace the vanilla Load/continue UI for runs containing the phantom, re-fabricate the phantom's lobby member with its original player ID *before* run-state deserialization validates identities, and only then let guests rejoin as themselves. Get this wrong and the failure mode is the worst kind — a corrupted-looking save mid-campaign with friends waiting.

### 4.3 Protocol tolerance: what the host may send to vanilla guests

If the companion later needs to communicate beyond ordinary play (e.g. an enhanced HUD for modded guests — out of scope for v1, but it shapes the architecture), the wire protocol has one hard rule worth knowing now. Messages are framed as `[4-byte type ID][8-byte sender NetId][payload]`, and on receipt each client instantiates the message class mapped to that ID via `Activator.CreateInstance` — the mapping is baked into the assembly, with **no skip/ignore branch for unknown IDs** ([straypixels.net](https://straypixels.net/sts2-multiplayer-architecture/)). Truly unknown frames sent to vanilla guests are therefore not tolerated by design — don't build on them. The working pattern in the ecosystem is **presence-gated custom messages**: mods like sts2_typing (synchronized chat) and BetterSpire2's teammate hand viewer register their own message types and work fine *because every recipient has the mod* ([Nexus Mods](https://www.nexusmods.com/slaythespire2/mods/169)). A future guest-side enhancement would follow the same pattern — modded guests check in with the host, which then serves them custom frames — while vanilla guests continue to receive nothing but vanilla traffic. For low-bandwidth extras with zero protocol risk, the AI can also simply use the vanilla chat channel, which is thematically appropriate for a companion.

## 5. A Concrete Implementation Roadmap

### 5.1 Recommended build order

Given the scope decision (host-only, vanilla guests), the build order is more direct than the general case. **Step one: decompile and map the lobby.** In `sts2.dll`, map the lobby, player-registry, command-dispatch, and message-dispatch classes — these are the mod's three integration points, plus the receive path you'll want to understand precisely (§4.3). **Step two: phantom player on the test transport.** Reproduce what KitLib's Pseudo Co-op mode does: fabricate a lobby member (NetId + ACK/command stream) on the internal local test lobby, and drive it with a trivial decision function — random or default choices are sufficient at this stage (KitLib's SyncBot already demonstrates default-choice driving), so no AI work is needed yet.

**Step three: prove the scoped claim.** Open a Steam P2P lobby, fabricate the phantom inside it, and have an unmodded friend join. This experiment decides the project: if the vanilla guest joins, sees the phantom as a normal player, and the sim holds through a combat, the host-only-with-vanilla-guests design is validated. **Step four: own the continue path — do this before any real campaign.** Since your group saves and loads routinely, replace/intercept the vanilla continue flow for phantom runs: re-fabricate the phantom with its saved player ID before identity validation, then let guests rejoin (§4.2). Test save → quit → resume cycles with a friend explicitly; a run that works start-to-finish but can't survive a Tuesday-night logout is not shippable for your use case. **Step five: the action layer, then the brain.** Mine sts2AITeammate's `Scripts/ActionLayer/` — the only public inventory of StS2's decision points (combat turns, end-turn ready handshakes, map votes, rewards, shops, campfires, event menus, potion prompts) and the wiring to observe state and actuate choices at each — and build your control layer on it: character assignment, vote mirroring, and the host-gated combat button with wake-up (§5.2) all live here, ahead of any policy work. Consult `docs/LIMITATIONS.md` for flows known to hang bots ([GitHub](https://github.com/SallyHong2347/sts2-ai-teammate)). Then plug in your own agent behind the control protocol. The control layer (not the policy) owns every mechanical confirmation — end-turn ready, votes, room-advance ready-ups — issuing defaults automatically, because a missed confirmation stalls the lobby for three humans while a missed card play is a harmless no-op. Throughout: keep the mod content-free (register nothing in ModelDb) so the consistency hash stays vanilla (§4.2).

### 5.2 Locked design decisions and their consequences

Three decisions are locked in, and each shapes the implementation in a specific way. **(1) The host player chooses the agent's character.** This is the simplest of the three: the phantom's lobby member needs a character selection message like any other player — the mod issues it from a host-side picker rather than letting the agent decide. It also means the mod must present its own small lobby UI (an "add agent" control and a character picker), since the vanilla lobby screen has no concept of adding a non-Steam participant.

**(2) Agents abstain from map votes and collaboration-event votes — or follow the host player.** Abstention is the risky half of this decision: if the game treats an uncast vote as "not ready," the map node will never resolve and the whole lobby stalls. So the mod must either auto-cast a vote mirroring the host player's (the safe default — votes are per-player messages, and mirroring is trivial to implement) or verify in the decompiled map-vote logic that phantom votes are genuinely not awaited. Do not assume abstention works; the follow-the-host variant is strictly safer and barely less convenient.

**(3) Host-gated combat turns with wake-up.** This is the most consequential lock-in, and its justification is UX and pacing, not netcode: StS2 already solves simultaneous-turn interleaving through its authoritative ActionQueue — the engineer's third article covers the `ActionQueueSynchronizer`, which "ensures that actions taken within combat are correctly ordered," and KitLib routes its own multiplayer cheats through that same queue precisely because it syncs on every peer ([straypixels.net](https://straypixels.net/sts2-multiplayer-architecture/), [KitLib CHANGELOG](https://github.com/WRXinYue/STS2-DevMode/blob/main/CHANGELOG.md)). An agent acting mid-turn is just one more command source into a pipeline built for four humans. Gating the agent behind a host-only UI button is therefore a *control* feature — the host decides when the bot moves, and a slow brain (e.g. an LLM) never holds up the lobby. The button itself is host-local UI, invisible to vanilla guests — exactly the kind of overlay the Modding Tutorial's GUI chapters cover.

Wake-up follows the design principle that **mechanical confirmations don't belong to the agent's policy**: end-turn is a formality the game requires to resolve the turn, so the phantom should confirm promptly like any polite player (holding back would stall everyone, since the game awaits all confirmations). "Wake up" is then purely the mod's control layer cancelling its own committed end-turn confirmation on the host's request and letting the agent act again. No exotic "standing by" state is needed — KitLib already manipulates this exact state (its changelog references "the per-player 'ready to begin enemy turn' check" ([KitLib CHANGELOG](https://github.com/WRXinYue/STS2-DevMode/blob/main/CHANGELOG.md))), so un-readying is at most a small Harmony patch over ground a reference project has already walked.

Remaining open choices are lighter. **Lobby slots**: each agent consumes one of four vanilla slots, so "3 friends + agent" needs the player-limit mod on every client — the one feature that genuinely cannot stay host-only ([Rain156/sts2-RMP-Mods](https://github.com/Rain156/sts2-RMP-Mods)). **Guest experience**: with vanilla guests as a hard requirement, everything the agent communicates rides vanilla channels — chat narration is free; anything richer waits for a real need (§4.3). **Save discipline**: for a group that resumes often, the mod's continue path is the feature your friends will touch most — make phantom identity stable across sessions (persist its player ID in the run state) and never let the vanilla Load button handle a phantom run. **Brain architecture** stays deliberately uncommitted: the control protocol above works with any policy behind it — random for bring-up, heuristics or an LLM later. Also settle the **social contract** early: modded and unmodded saves are separate and modded runs typically disable achievement tracking ([Nexus Mods](https://www.nexusmods.com/slaythespire2/mods/2), [XMODHub](https://www.xmodhub.com/info/blog/best-slay-the-spire-2-mods-guide/)); even though guests install nothing, tell them the fourth player is a host-side bot.

## 6. Risks, Caveats, and Honest Unknowns

The dominant risk is **temporal, not technical**: everything in this report describes an Early Access game at v0.10x in October 2026, and the loader contract, internal class shapes, and multiplayer flows will keep shifting until 1.0. The community handbook itself pins its guidance to specific commits and instructs modders to re-verify `release_info.json` and `sts2.dll` on every update ([StS2 Modding Tutorial](https://fresh-milkshake.github.io/Modding-Tutorial/)). Your mod's maintenance burden is proportional to how deep its Harmony patches reach — and an AI companion necessarily reaches deep, into lobby management and decision-point handling, the two areas every existing project flags as most fragile.

The genuine unknowns are narrow and testable rather than fundamental. The one that matters for the scoped design — whether a host-fabricated phantom works in a **Steam P2P lobby with vanilla guests**, as opposed to the proven LAN/test transport — is a single prototype experiment, not a research project (§5.1, step three). Secondary unknowns: whether Mega Crit tightens the `affects_gameplay` semantics or the join handshake in a future patch, and whether they eventually formalize scripted-player support (their roadmap does mention "experimental game modes" ([Yelzkizi](https://yelzkizi.org/slay-the-spire-2-roadmap-explained-no-release-dates/))). And AI play quality remains what it is: today's heuristic teammates misread situations, and LLM teammates burn millions of tokens to play at an amusingly mediocre level. None of these caveats change the headline conclusion — they define the engineering budget, not the feasibility.

## 7. Bottom Line

Running multiple characters from one host, some controlled programmatically, is not just possible in Slay the Spire 2 — it has been done publicly, repeatedly, and with source code available: **sts2AITeammate** proves multiple AI-driven characters inside one host process; **KitLib** proves a host-fabricated phantom player can share a lobby with a real remote client; **STS2-Agent** and **neuro-sts2** prove AI-driven members of real lobbies; and **Plapla's Couch Co-op** — the mod you remembered — proves the host can serve players that aren't game clients at all. The deterministic, command-based multiplayer architecture Mega Crit's own engineer describes makes a headless player a first-class citizen by construction.

The scoped design — host-only mod, vanilla guests, no guest mods — hangs on a single unproven link (phantom member in a Steam P2P lobby) that one afternoon of prototyping resolves. If it holds, the rest is integration work against the reference projects in the appendix, with sts2AITeammate's MIT-licensed action layer as the map for driving every decision point of a run. Build it, and you'd be shipping something the community's mod round-ups already describe as desirable — reviewers praised Sally's bot mod precisely because it lets groups play co-op "without finding other players" ([AllThingsHow](https://allthings.how/slay-the-spire-2-mods-worth-installing-right-now/)).
